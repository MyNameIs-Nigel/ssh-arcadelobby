# Fleet deploy

Bootstraps the single EC2 host that runs the whole fleet (docs/04's
topology: one host, one Elastic IP, the router public on 22, every game
private). See `docs/04-deployment-and-cicd.md` for the full architecture
and `docs/06-fleet-data-durability.md` for the S3/Litestream durability
story this stack wires into.

## Fresh host bootstrap

1. **Install Docker + the compose plugin** (Ubuntu/Debian):

   ```bash
   curl -fsSL https://get.docker.com | sh
   sudo apt-get install -y docker-compose-plugin
   sudo usermod -aG docker "$USER"   # re-login for this to take effect
   ```

2. **Lay out the directory** the compose file expects:

   ```bash
   sudo mkdir -p /srv/ssharcade
   sudo chown "$USER" /srv/ssharcade
   cd /srv/ssharcade
   ```

3. **Copy the deployed files** from this repo (or let the CI rsync step do
   it later — see docs/04's "Compose changes" section):

   ```bash
   cp deploy/docker-compose.yml deploy/games.toml /srv/ssharcade/
   ```

4. **Provision secrets** (one-time per host — the proxy key is never
   generated by any container; it's the router's identity when it dials
   into every game, so it's provisioned by hand and never lives in git):

   ```bash
   cd /srv/ssharcade
   mkdir -p secrets
   ssh-keygen -t ed25519 -N "" -f secrets/proxy_key -C "ssharcade-router"
   cp secrets/proxy_key.pub proxy_keys   # the games' trust file
   # Readable by the containers: Docker Compose file-based secrets and
   # bind mounts both preserve the source file's own permissions, and the
   # game containers run as a non-root uid (65532) that doesn't match
   # whichever host user generated the key — 600 (owner-only) leaves every
   # game unable to read its own trust file, and the router unable to read
   # its own proxy key, both failing with "permission denied" at boot.
   chmod 644 secrets/proxy_key proxy_keys
   ```

5. **First boot**:

   ```bash
   docker compose up -d
   docker compose ps       # router should be Up; farm should be Up
   ssh -p 22 <host>        # menu should appear
   ```

   `moonminer` and `idlefarmer` will fail to pull or won't bridge identity
   correctly yet — see the readiness notes at the top of
   `docker-compose.yml`. That's expected; the menu shows them `○ OFFLINE`
   rather than breaking anything else (docs/04's acceptance criteria).

## Durability (S3/Litestream)

Uncommented by default — the stack runs in dev mode (no AWS credentials
required) until you provision a bucket. One-time setup (docs/06):

1. Create a **versioned**, SSE-S3-encrypted, public-access-blocked S3
   bucket in the instance's own region.

2. Attach this policy to the **EC2 instance profile** — litestream's AWS
   SDK picks it up automatically, no keys anywhere in this repo, the
   compose file, or any image. `ListBucket` needs the bare bucket ARN;
   the read/write/delete actions need the `/*` form — a common IAM
   gotcha if both end up on the same ARN.

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Sid": "ListBucketScoped",
         "Effect": "Allow",
         "Action": ["s3:ListBucket"],
         "Resource": "arn:aws:s3:::<bucket-name>"
       },
       {
         "Sid": "ObjectReadWriteDelete",
         "Effect": "Allow",
         "Action": [
           "s3:GetObject",
           "s3:PutObject",
           "s3:DeleteObject",
           "s3:AbortMultipartUpload",
           "s3:ListMultipartUploadParts"
         ],
         "Resource": "arn:aws:s3:::<bucket-name>/*"
       }
     ]
   }
   ```

3. `mc` (used only for the small host-key/proxy-key objects under
   `keys/`) has no instance-role support, so it separately needs its own
   IAM **user** (not the instance role) with a static access key/secret,
   set via `MC_HOST_s3` in each service's environment (see the
   commented-out block in each `docker-compose.yml` service). Scope this
   one tighter than the instance role — `mc` only ever touches `keys/`,
   never the per-game `db/` objects, and never deletes anything:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Sid": "ListKeysPrefixOnly",
         "Effect": "Allow",
         "Action": ["s3:ListBucket"],
         "Resource": "arn:aws:s3:::<bucket-name>",
         "Condition": { "StringLike": { "s3:prefix": "keys/*" } }
       },
       {
         "Sid": "KeyObjectsReadWrite",
         "Effect": "Allow",
         "Action": ["s3:GetObject", "s3:PutObject"],
         "Resource": "arn:aws:s3:::<bucket-name>/keys/*"
       }
     ]
   }
   ```

4. Uncomment the `LITESTREAM_*`/`*_MC_PATH`/`MC_HOST_s3` lines for `farm`
   (and `router`, for its own `keys/router/` backup) with your real bucket
   name, then `docker compose up -d`.

Restore/kill drills for this stack are `ssh-farm`'s
`scripts/restore-drill/` (`kill-drill.sh`, `restore-to-scratch.sh`,
`no-credentials-check.sh`) — reused fleet-wide per doc 06's "the drill
script lives in ssh-farm" rule. Run them against a real bucket before
trusting this in production; this repo's own validation only confirms the
compose file parses and the router's own image builds/restores its keys
correctly (see docs/04's acceptance criteria for what still needs a live
EC2 host: the instance-loss drill and the public port scan).

## Redeploying a single service

CI does this automatically on merge to `main` (docs/04's per-repo
`release.yml`); by hand:

```bash
cd /srv/ssharcade
docker compose pull farm
docker compose up -d farm    # only this service restarts; others unaffected
```

## Rotating the proxy key

```bash
ssh-keygen -t ed25519 -N "" -f secrets/proxy_key.new -C "ssharcade-router"
cat secrets/proxy_key.new.pub >> proxy_keys   # append, don't replace yet
docker compose restart moonminer idlefarmer   # (once they trust proxy_keys)
mv secrets/proxy_key.new secrets/proxy_key
docker compose restart router
# once confident, remove the old public key line from proxy_keys and
# restart the games once more
```
